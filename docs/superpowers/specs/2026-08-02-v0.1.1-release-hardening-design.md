# NanoEvolve v0.1.1 Release Hardening Design

Date: 2026-08-02

Status: Approved design

## 1. Objective

NanoEvolve v0.1.1 turns the validated v0.1 implementation into a repository that can be published and maintained with credible automation and documentation.

This milestone does not add a new evolution algorithm. It strengthens executable entry points, package metadata, continuous integration, source-distribution contents, release checks, and contributor-facing documentation.

## 2. Success Criteria

The milestone is complete when:

1. Both `nanoevolve` and `python -m nanoevolve` expose the same CLI.
2. `nanoevolve --version` and `python -m nanoevolve --version` report the installed package version.
3. Tests run on supported Python versions and major desktop CI platforms.
4. Wheel and source-distribution artifacts build successfully.
5. A clean environment can install the wheel and run import, version, demo, and CLI smoke checks.
6. The wheel declares no runtime dependency.
7. The source distribution contains the project documentation, examples, tests, and design records needed by contributors.
8. English and Chinese README files remain structurally synchronized.
9. Contributor, security, and changelog documents describe the real project boundary.
10. No unknown author, license, repository URL, or release destination is fabricated.

## 3. Scope

### 3.1 Included

- Module execution through `python -m nanoevolve`.
- CLI and module `--version` support.
- One authoritative package-version source.
- Python package classifiers and keywords.
- Typed-package marker through `py.typed`.
- Explicit source-distribution manifest.
- GitHub Actions test and package-build workflows.
- Standard-library release-check script.
- `CONTRIBUTING.md`, `SECURITY.md`, and `CHANGELOG.md`.
- Synchronized English and Chinese README release sections.
- Tests for version and module entry points.
- Build, wheel-install, and source-distribution verification.

### 3.2 Excluded

- Git initialization, branches, commits, tags, or pushes.
- A remote Git repository or GitHub project creation.
- Author or maintainer identity.
- License selection.
- Homepage, repository, issue-tracker, or documentation URLs.
- PyPI upload or package-name reservation.
- Signed releases, trusted publishing, or release attestations.
- Paid model calls or real benchmark execution.
- v0.2 SEARCH/REPLACE mutation.

## 4. Version Ownership

`pyproject.toml` remains the authoritative version declaration.

Runtime code resolves the installed version through:

```python
importlib.metadata.version("nanoevolve")
```

When running directly from an unpackaged source tree, the package exposes a clearly marked fallback version rather than duplicating a second manually maintained version constant.

The public package exports `__version__`.

The CLI supports:

```bash
nanoevolve --version
python -m nanoevolve --version
```

Both commands must return the same value as `importlib.metadata.version("nanoevolve")` after installation.

## 5. Module Entry Point

Add:

```text
nanoevolve/__main__.py
```

Its only responsibility is to call `nanoevolve.cli.main()` and exit with the returned status code.

It contains no parser, model, archive, or error-handling logic.

## 6. Package Metadata

`pyproject.toml` adds only metadata that can be asserted without external identity:

- Python implementation and version classifiers.
- Operating-system-independent classifier.
- Development-status classifier.
- Topic classifiers related to artificial intelligence and software development.
- Search keywords.
- Inclusion of `nanoevolve/py.typed` as package data.

The project does not add:

- `authors` or `maintainers`.
- `license` or license classifiers.
- `project.urls` entries.

Those fields remain absent until the owner supplies authoritative values.

## 7. Distribution Contents

### 7.1 Wheel

The wheel contains only the importable `nanoevolve` package, including `py.typed`, and standard package metadata.

It does not contain tests, examples, task ledgers, or design documents.

### 7.2 Source distribution

`MANIFEST.in` explicitly includes:

```text
README.md
README.zh-CN.md
CHANGELOG.md
CONTRIBUTING.md
SECURITY.md
pyproject.toml
docs/superpowers/specs/*.md
examples/**/*
tests/**/*
tasks/*.md
```

It excludes caches, virtual environments, generated archives, build outputs, and `.nanoevolve` run state.

The release verification inspects archive member names rather than assuming setuptools defaults.

## 8. Continuous Integration

Add:

```text
.github/workflows/ci.yml
```

### 8.1 Test matrix

The matrix covers:

```text
Ubuntu: Python 3.11, 3.12, 3.13
Windows: Python 3.12
macOS: Python 3.12
```

Each matrix entry performs:

```bash
python -m pip install --upgrade pip
python -m pip install -e .
python -m unittest discover -s tests -v
python -m compileall nanoevolve examples
python -m nanoevolve --version
python examples/hello_evolve/demo.py
```

The demo is deterministic and makes no network request.

### 8.2 Package job

A separate Ubuntu job performs:

```bash
python -m pip install --upgrade pip build
python -m build
```

It then:

1. Inspects wheel and source-distribution contents.
2. Creates a clean virtual environment.
3. Installs the built wheel.
4. Verifies version output.
5. Verifies zero declared runtime dependencies.
6. Runs the deterministic demo and `best`/`inspect` smoke commands.

The CI workflow does not publish artifacts to PyPI.

## 9. Release Check Script

Add:

```text
scripts/release_check.py
```

The script uses only the Python standard library and runs from the repository root.

It verifies:

1. Complete unittest discovery.
2. `compileall` for package and examples.
3. English and Chinese README section-count parity.
4. Required README concepts and CLI command names.
5. Absence of `TODO`, `FIXME`, `TBD`, and placeholder repository URLs in release-facing files.
6. Core line-count budget at or below 1,250 lines for `types`, `mutation`, `archive`, `runner`, and `engine` combined.
7. `pyproject.toml` contains no runtime dependencies.
8. `pyproject.toml` version matches the expected stable version format.
9. Required contributor and security files exist.

The script prints each check before running it and exits non-zero on the first failed command or invariant.

Wheel and source-distribution building remain CI responsibilities because the `build` package is a development tool, not a runtime dependency.

## 10. Contributor Documentation

### 10.1 CONTRIBUTING.md

The contributor guide contains:

- Supported Python versions.
- Editable installation.
- Test, compile, demo, and release-check commands.
- TDD expectations.
- Six-module architecture boundary.
- Rules against adding hidden workflow systems or runtime dependencies without design approval.
- Pull-request checklist.

It does not invent a code-of-conduct URL or issue tracker.

### 10.2 SECURITY.md

The security policy states:

- Supported version: current `0.1.x` development line.
- `SubprocessRunner` is not a security sandbox.
- Untrusted generated code must run inside external isolation.
- API keys are filtered from evaluator environments by name.
- Vulnerabilities should be reported privately through the eventual repository hosting platform rather than public issue content.

It does not provide an invented email address.

### 10.3 CHANGELOG.md

The changelog uses a Keep-a-Changelog-compatible shape without claiming a release date that has not occurred.

It contains:

- `Unreleased` for v0.1.1 release-hardening work.
- `0.1.0` dated 2026-08-02 for the validated Nano core implementation.

The changelog distinguishes algorithmic capabilities from release infrastructure.

## 11. README Updates

Both README files add corresponding sections for:

- Version and module-entry commands.
- CI and release verification.
- Contributor and security documents.
- Package build boundaries.

The English and Chinese structures remain aligned.

No CI badge is added until a real repository owner/name makes the badge URL valid.

Static badges continue to describe only verifiable local facts.

## 12. Testing

Add tests that verify:

- `nanoevolve.__version__` is a non-empty string.
- Installed metadata and exported version agree when metadata is available.
- `python -m nanoevolve --version` succeeds.
- `nanoevolve.cli.main(["--version"])` exits successfully through argparse behavior.
- `py.typed` is present in an installed wheel.
- The release-check script succeeds in the working tree.

Existing 45 tests remain mandatory.

## 13. Risks and Mitigations

### Cross-platform subprocess behavior

The Windows and macOS matrix may expose path, signal, or process-timeout assumptions. Fixes remain within the current runner contract; CI-specific skips are not the default response.

### Build-tool dependency confusion

`build` is installed only in the package job. It is not added to runtime dependencies.

### Invalid public metadata

Unknown identity and repository fields remain absent rather than using placeholders.

### Documentation drift

The release-check script enforces structural README parity and required concepts, while human review remains responsible for translation quality.

## 14. Acceptance Commands

Local acceptance uses:

```bash
python -m unittest discover -s tests -v
python -m compileall nanoevolve examples
python scripts/release_check.py
python -m nanoevolve --version
```

Package acceptance additionally uses an isolated environment and `python -m build` when the build tool is available.

## 15. Decision Summary

The approved v0.1.1 strategy is:

1. Harden publication and maintenance before adding v0.2 algorithms.
2. Add executable and version entry points without duplicating CLI logic.
3. Verify multiple Python versions and major desktop platforms in CI.
4. Build and inspect both wheel and source distributions.
5. Keep build tools out of runtime dependencies.
6. Publish contributor, security, and changelog documentation.
7. Avoid invented identity, license, repository, or release information.
8. Preserve the minimal algorithmic core unchanged except for defects exposed by cross-platform validation.
